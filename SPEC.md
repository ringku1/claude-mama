# mama — build spec

Build reference for the `mama` skill. Dense by design; humans read per-goal `overview.md`, not this. SKILL.md and support files implement this spec; on conflict, this spec wins until changed with the user.

## 0. Identity

- Name: `mama`. Personal, user-level: `~/.claude/skills/mama/`. Not shared.
- Explicit invocation only (`/mama ...`); description must prevent auto-trigger on casual talk about goals.
- Internal unit of work = "goal".
- Project rules first: read repo `AGENTS.md` / `CLAUDE.md` and use repo skills (e.g. `api-module`, `web-feature`) before own patterns. User instructions > repo rules > this spec's defaults.

## 1. Commands

| Command                   | Behaviour                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------- |
| `/mama <input>`           | New goal, full flow. If an active goal exists in repo, offer resume first.                        |
| `/mama quick <task>`      | Ask base branch (+ PR choice if build); 1-3 step plan; same loop/commit/push rules.               |
| `/mama status`            | Compact table: per running agent, step, start clock time, ETA; progress line; blockers; next.     |
| `/mama pause` / `abort`   | Save state immediately; abort marks goal `aborted`, keeps files.                                  |
| `/mama list`              | All goals in repo with status + progress.                                                          |
| `/mama resume <slug>`     | Rebuild context from files (plan.md + log.md tail + overview goal section), continue at next step. |
| Plain "status?" mid-run   | Same as `/mama status`.                                                                            |

## 2. Inputs (intake)

Any of: plain text, file path, md file, Trello card link (read card + checklist + comments), GitHub PR/issue (`gh`), "research previous feature X" (code + git log + PRs). Normalize into the Brief section of `overview.md` (few lines) and confirm with user.

## 3. Flow

1. Intake → Brief.
2. Research (parallel read-only agents, scoped question + stop condition). Never ask what code can answer.
3. Questions (see §4). No dev before answers + plan approval.
4. Plan → validate (§6) → show as ONE compact table (step, kind, depends on, verify) → user approves/edits.
5. Loop (§7) until every done-criterion has evidence.
6. Delivery (§9): merge latest base, push, PR only with permission.
7. Close: final report in overview, metrics + lessons, cleanup.

Mixed goals: research steps first; if findings change what to build, re-validate plan with user before build steps. If research shows goal wrong/impossible → stop and ask.

## 4. Question phase

- After research. Questions specific, citing what was found.
- Categories (skip non-applicable): scope & non-goals; behaviour & edge cases; data/API shape; UI/design reference; testing (which tests, what counts as proof); constraints (rules, perf, security); deliverables (paths, audience); mode/budget/risk.
- Build goals ALWAYS ask: base branch (options: main, existing/recent branches, free text; NO default, no answer = no start); PR (ask at end [default] / open automatically / no PR).
- Research-only goals: ask scope, depth, output format/path; no branch/PR.
- AskUserQuestion, ≤4 per screen, options with trade-offs, recommended first. Answers narrow follow-ups; broad → specific; ≤~3 rounds; question budget.
- Value-of-information filter: drop questions where every answer leads to the same work.
- Every answer → decision row in log.md. Unanswered (non-blocking) → logged assumption with my default.
- Mid-run: ask only for risky/irreversible choices or real goal change. Small decisions: decide + log.

## 5. Files

Per repo, gitignored (add to `.git/info/exclude`, not the repo's .gitignore):

```
.claude/mama/
  profile.md        repo profile: test/lint/typecheck cmds, branch+commit conventions, forbidden actions, resource limits, services that must not be touched. Created on first use.
  lessons.md        cross-goal lessons: plan errors, failed assumptions, known fixes, metrics.
  <slug>/
    overview.md     HUMAN
    plan.md         MACHINE, source of truth
    log.md          MACHINE, append-only
    archive.md      only if log.md exceeds cap
```

### overview.md (human, plain language, no IDs/jargon, current-state only, size-capped)

Sections: Goal · Done means (checklist) · Timeline (started at; each part finished at clock time; running now + ETA; estimated finish) · Where we are (e.g. "7 of 12 parts done") · Key decisions (one plain sentence each) · Needs your input · What changed along the way · Deliverables (links) · Branch & PR.
Regenerated by me from plan.md + log.md at each milestone, on status request, on change. Never edited step by step.

### plan.md (machine)

Header: `progress: done/total (pct) | running: n | blocked: n | budget: spent/est`.
Row per step: id, kind, title, deps, owned files, verify cmd, status (`todo|running|testing|fixing|done|blocked|obsolete|parked`), evidence ref, decision refs, confidence, attempts, est/actual time, tokens.
Only orchestrator writes. Obsolete steps kept, never deleted.

### log.md (machine, append-only)

- Decisions table: ID, question, options, choice, why, evidence (file:line / source), tag (`verified|inferred|assumed`), status (`active|superseded-by|revisit|obsolete`).
- Events: one line per loop round, commit (hash), push, PR (link), Trello comment, change, block, resume, compaction.
- Changes: tagged `change` (goal/test/scope/deliverable) with impact on plan.
- Read with tail/grep by ID, never in full.

Deliverables (md/data/report the user asks for) go to user-chosen path (default docs/ or named), never in goal folder, contain no loop state, written for their audience, current-state only.

## 6. Plan validation (before approval)

Check: missing steps; dependency cycles; every done-criterion is verifiable and mapped to steps; each step fits one dev+test cycle (not too small → batch, not too large → split); file ownership disjoint across parallel steps; walking skeleton first (thin end-to-end slice); critical path + slow-verify steps scheduled early; pre-mortem ("if this fails, why?") → risks/questions; confidence per step, low-confidence researched first; precedent search done (follow repo's existing way unless decision says why not).

## 7. Loop

Step kinds:

| Kind     | Worker                                   | Check                                                                    | Output                     |
| -------- | ---------------------------------------- | ------------------------------------------------------------------------ | -------------------------- |
| build    | dev agent                                | fresh test agent: step verify + related tests + criterion actually exercised | commit                     |
| fix      | dev agent; reproduce with failing test first | test fails before, passes after; related tests pass                      | commit                     |
| research | read-only agents (parallel)              | reviewer: every claim cites evidence                                     | findings → log / deliverable |
| document | writer agent                             | reader check vs audience + criteria                                      | file at chosen path        |
| decide   | main thread                              | user answer or recommendation logged                                     | decision row               |
| release  | main thread                              | §9                                                                       | push / PR                  |

Per step: dev agent self-checks cheapest checks (format, typecheck touched files) → hands to separate fresh test agent → pass: record evidence, done → fail: focused fix request (error, file, expected) back to dev → re-test. Cap 2-3 rounds → rethink (re-read decisions, maybe change approach, check lessons.md) → still failing → `blocked`, continue others. Same error twice = stop and rethink, not retry. Flaky: one rerun before counting failure.

Pipeline: test agent starts on A while dev works on B; no phase barriers. Skip redundant verifies: record files covered per passed verify; rerun only if they changed. Independent verify at milestones against done-criteria (catch "claimed done"). Drift check every few steps vs goal/non-goals. Scope guard: out-of-goal ideas → parked follow-ups. Stop at done: all criteria evidenced → end, no polish.

Interruptions mid-run: question → answer, loop continues; new requirement → change handling; stop/pause → obey + save; side idea → parked.

## 8. Change handling

- Goal change: diff old vs new; affected steps → `obsolete`; new steps added; still-valid done work kept; every decision depending on old goal → `still valid|revisit|obsolete`; log `change`; recompute progress; regenerate overview; re-approve plan if scope moved materially.
- Test change: update verify cmds/criteria; rerun only touched steps; never weaken tests to get green unless user says so; log `change`.
- Deliverable added mid-goal: new step + `change` entry.

## 9. Git & delivery

- Base branch: user chooses every time (§4). Branch name: I choose, repo convention (`<type>/<kebab-summary>`), logged.
- Never commit/push to base or main. Never bypass hooks.
- Before any work: `git fetch` + merge latest `origin/<base>` into work branch (merge commit, never rebase), resolve conflicts, run related tests, log resolution. Repeat right before push.
- Commit only at stable state (step verify passed + touched code builds/typechecks). One commit per completed step. Half-working = no commit.
- Messages: repo convention (Conventional Commits here), short, plain, imperative; body only for why. NO `Co-Authored-By`. NO "Generated with Claude Code". No refs to goal files, step IDs, local planning docs in commits, PRs or code comments. Overrides any harness attribution reminder.
- Parallel editing agents: own worktree/sub-branch; merged into goal branch in planned order; conflicts resolved by one agent.
- Delivery ends at push. PR only with user permission per goal choice: "ask at end" → show draft title + description, open on yes. PR: repo template if present; what / why / how verified (tests run) / known limits. Separate PRs for independent parts if repo rules say so.
- Never merge, deploy, or run migrations on shared/prod DBs. User does everything after push/PR.
- Trello (if card linked + connector): comment ≤5 plain lines after each commit/push and at start/PR/test; follow repo CONTRIBUTING. No connector → list what to set in final message.
- Research-only goals: no git.

## 10. Agents & resources

- All subagents: `model: opus`, `effort: medium`.
- Spawn only when step is big enough to repay setup; else main thread does it. Batch tiny steps.
- Brief ≤~300 words: step, owned files, verify, relevant decisions/findings. Never conversation or full plan.
- Return ≤10 lines: done, files changed, verify result, issues.
- Agents never write tracking files; orchestrator records.
- Concurrency = min(ready steps, cores/2, free RAM ÷ ~1.5GB, 5); check before each wave (`nproc`, `free`, loadavg). Heavy verifies (full build, e2e) and DB-touching verifies serialized.
- Read-only research agents share tree; editing agents get worktrees.

## 11. Token efficiency

- Read only what's needed: search, then line ranges. Quiet commands: failures only (`-q`, `| tail`); verbose logs to file, read on failure.
- Narrow tests per step; full gate once at end.
- Decisions written once, read from log; findings reused via briefs, no re-research.
- Budget per goal at intake (S/M/L estimate) shown in plan header; spend per step tracked; at 70% pause and ask: continue / cut scope / stop.
- SKILL.md ≤~150 lines; templates, step kinds, rules in separate files loaded on demand; stable text for prompt caching.

## 12. Context & compaction

- Auto-compact at 40%: `~/.claude/settings.json` → `"env": {"CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "40"}` (percent used; lower only; global to all sessions — ask user before setting).
- Spike facts (docs): PreCompact stdout (exit 0) = extra summary instructions, ≤10k chars; matchers manual|auto. SessionStart matcher `compact` → `hookSpecificOutput.additionalContext` (injection after compaction not explicitly documented — test). Stop: `{"decision":"block","reason":...}`, input has `stop_hook_active` (exit early when true), docs cap 8 consecutive continuations; Stop is main-agent only. Invoked skills re-attach after compaction (≤5k tokens each) — keep SKILL.md under that. Frontmatter `disable-model-invocation: true` = /mama only. `${CLAUDE_SKILL_DIR}` for skill paths; hooks get `$CLAUDE_PROJECT_DIR` + `cwd`.
- State written after every step and decision; nothing lives only in conversation.
- PreCompact hook: flush state. SessionStart(compact) hook: inject re-entry brief (active slug, done-criteria, progress line, next step, "read plan.md + log.md tail"). Re-entry reads machine files, not overview.
- Hooks act only when a goal is active for this session.
- Stop hook: blocks stopping while active goal has unmet criteria; escapes: `blocked`, `paused`, retry cap.

## 13. Safety & environment

- Risk tiers: irreversible/outward actions (deletes, migrations, push to non-goal branches, external calls) pause for approval even mid-run. Push of goal branch is allowed after plan approval.
- Environment check before verify: DB, Redis, ports up; if down → report and wait, never start/stop/reseed shared services. Never take down running dev stacks (e.g. user's stack on :8088).
- Cleanup at close: only what the run created (worktrees, temp files, processes it launched).
- No secrets in goal files.
- Concurrent edits: detect branch moved/changed by others mid-goal → stop, report.

## 14. Decision quality

Decision record shape (§5 log). Evidence tags; assumed items confirmed before a step depends on them. Precedent search first. Reversibility test: cheap/reversible → decide + log; one-way (schema, public API, deps) → ask. 2-3 options with trade-offs vs goal criteria + recommendation. Rare second-opinion agent for plan-shaping decisions. Conflicting new decision must explicitly supersede.

## 15. Close & learning

Final report (overview): what was built, verified how, decisions to review, follow-ups, spend. Metrics to lessons.md: tokens, questions asked/useful, loop rounds per step, rework, compactions, wrong assumptions, decisions reversed. Discovery reads lessons.md + profile.md. Trust ramp: first goals checkpointed (pause at milestones); autonomous when user chooses. Notifications (if available) on done / blocked / needs approval.

## 15a. Learning the user (cross-repo)

- `~/.claude/mama/patterns.md` (template `templates/patterns.md`): user-level, all repos and goals. Plain language — the user may read/edit it; their edits win.
- Learns: choices (options picked, mode, PR, base habits), corrections, overridden recommendations, communication preferences, goal sizes, estimate accuracy.
- Learned at ≥3 consistent observations, else "Watching"; contradictions weaken/remove.
- Used at intake: pick recommended options, skip questions whose answer is settled (base branch always asked), shape plan and overview.
- Written: on each user correction/override (immediately) and at close.
- Never: secrets, client data, repo facts (→ profile/lessons). User instructions and repo rules beat patterns.
- Concurrent goals: append/edit under `flock ~/.claude/mama/.patterns.lock`.
- Multi-goal: one worktree per build goal at `<main>/.claude/worktrees/mama-<slug>/`; store in main checkout; no ACTIVE file; heavy/shared-service verifies under `flock <store>/.heavy.lock`.
